## 2. SLO ба Error Budget Тооцоо

| Сценарио | SLI (юуг хэмжих) | Босго | Цонх / Нөхцөл |
| :--- | :--- | :--- | :--- |
| **Performance** | `/cart/add` latency | p(95) < 50ms | 20 VU тогтмол ачаалалд, 1 мин |
| **Reliability** | `/pay` error rate | rate < 8% (0.08) | 20 VU, 1 мин |
| **Availability** | Нийт хүсэлтийн амжилт | checks rate > 90% (0.90) | 20 VU, 2 мин (10с зогсолттой) |
| **Report (Нэмэлт)** | `/report` latency | p(95) < 450ms | 20 VU, 1 мин |

### Босго сонгосон үндэслэл
1. **`/cart/add` (50ms):** Localhost дээр сагсанд нэмэх үйлдэл 1-5ms-т хариулдаг тул 50ms нь бодитой босго юм.
2. **`/pay` (8%):** `server.js` дотор ~5%-ийн санамсаргүй алдаа (HTTP 500) суулгасан тул 8% босго нь статистик хэлбэлзлийг харгалзсан зөв SLO юм.
3. **`/report` (450ms):** Код дээр 200-400ms санамсаргүй саатал бичсэн тул p(95) нь 450ms-ээс бага байх ёстой.
4. **Availability (90%):** 2 минутын (120 секунд) туршилт дунд 10 секундын зогсолт нь цагийн хувьд ~8.33% учир 90%-ийн босго тохиромжтой.

### Error Budget Тооцоо
- **Цагаар тооцсон budget:** 2 минутын (120 секунд) 10% нь **12 секунд** байна. 10 секундын зогсолт нь 12 секундын budget дотор багтана.
- **Хүсэлтээр тооцсон budget ба зөрүүний тайлбар:** Сервер унах үед хүлээх цаг (latency) байхгүй болж TCP Connection Refused агшин зуур буцаж ирдэг. Иймд зогсолтын 1 секундэд хэвийн үеэс хавьгүй олон хүсэлт шидэгдэж "идэгддэг". Иймээс цагаар тооцсон 10%-ийн budget нь хүсэлтийн тоогоор тооцоход 10%-иас илүү алдааны хувь үүсгэж зөрдөг.

## 4. Chaos ба FAIL Туршилтын Анализ

### Chaos Туршилтын үр дүн:
- Сервер 10 секунд зогсоход `http_req_failed` огцом өсөж, HTTP connection refused алдаанууд гарсан.
- `/pay` endpoint сервер унасан үед шууд бүтэлгүйтэж байсан тул **Reliability SLO** болон **Availability SLO** хоёр нэгэн зэрэг FAIL төлөвт орсон.
- **Availability ба Reliability SLI-г тусгаарлах:** Availability-г зөвхөн сүлжээний холболт ба серверийн амьд эсэхийг шалгах health-check endpoint-оор, харин Reliability-г зөвхөн ажиллаж байгаа серверийн бизнесийн логик алдаагаар (5xx codes) тусгаарлан хэмжиж болно.

### FAIL Туршилт ба Exit Code:
- `slo-test-fail.js` дээр `/report`-ын threshold-ийг `p(95)<100` болгоход k6 тухайн threshold дээр **FAIL (✗)** заасан.
- k6 ажиллагаа дуусахад буцаасан **Exit Code = 99** (эсвэл тухайн орчноос хамаарч 1) гарсан. CI/CD Pipeline яг энэ exit code zero биш байгааг мэдэрч build-ийг автоматаар зогсоодог.

## 5. Дүгнэлт

Сценарионоос SLO, улмаар k6 threshold руу шилжихэд хамгийн хэцүү нь бодит систем дээрх хэмжүүрүүдийг хэт өөдрөг биш, бас хэт сул биш бодитой тодорхойлох явдал байлаа. Chaos туршилт нь availability-г зөвхөн цагаар хэмжих нь хангалтгүй, хүсэлтийн давтамж болон failure rate-д шууд нөлөөлдгийг батлан харууллаа. localhost дээр хурдан ажиллах endpoint болон санамсаргүй сааталтай endpoint-уудыг k6 tag ашиглан ялгаж тестлэх нь чанарын баталгаажуулалтад маш чухал автоматжуулалт болдог юм байна.
