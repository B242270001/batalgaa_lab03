## 2. SLO ба Error Budget Тооцоо

| Сценарио | SLI (юуг хэмжих) | Босго | Цонх / Нөхцөл |
| :--- | :--- | :--- | :--- |
| **Performance** | `/cart/add` latency | p(95) < 50ms | 20 VU тогтмол ачаалалд, 1 мин |
| **Reliability** | `/pay` error rate | rate < 8% (0.08) | 20 VU, 1 мин |
| **Availability** | Нийт хүсэлтийн амжилт | checks rate > 90% (0.90) | 20 VU, 2 мин (10с зогсолттой) |
| **Report (Нэмэлт)** | `/report` latency | p(95) < 450ms | 20 VU, 1 мин |

### Босго сонгосон үндэслэл
1. **`/cart/add` (50ms):** Localhost дээр сагсанд нэмэх үйлдэл 1-5ms-т хариулдаг тул 50ms нь бодитой босго юм.
2. **`/pay` (8%):** `server.js` дотор ~5%-ийн санамсаргүй алдаа (HTTP 500) суулгасан тул 8% босго нь статистик хэлбэлзлийг харгалзсан зөв SLO юм.
3. **`/report` (450ms):** Код дээр 200-400ms санамсаргүй саатал бичсэн тул p(95) нь 450ms-ээс бага байх ёстой.
4. **Availability (90%):** 2 минутын (120 секунд) туршилт дунд 10 секундын зогсолт нь цагийн хувьд ~8.33% учир 90%-ийн босго тохиромжтой.

### Error Budget Тооцоо
- **Цагаар тооцсон budget:** 2 минутын (120 секунд) 10% нь **12 секунд** байна. 10 секундын зогсолт нь 12 секундын budget дотор багтана.
- **Хүсэлтээр тооцсон budget ба зөрүүний тайлбар:** Сервер унах үед хүлээх цаг (latency) байхгүй болж TCP Connection Refused агшин зуур буцаж ирдэг. Иймд зогсолтын 1 секундэд хэвийн үеэс хавьгүй олон хүсэлт шидэгдэж "идэгддэг". Иймээс цагаар тооцсон 10%-ийн budget нь хүсэлтийн тоогоор тооцоход 10%-иас илүү алдааны хувь үүсгэж зөрдөг.

## 3. Дүгнэлт (Conclusion & Analysis)

Энэхүү лабораторийн ажлын хүрээнд Express.js дээр суурилсан веб серверийн ажиллагааг k6 багаж ашиглан SLO болон Threshold-д суурилан туршиж үзлээ. Үндсэн ачааллын туршилт буюу `pass.txt` дээр бүх SLO босго үзүүлэлтүүд амжилттай биелж, систем хэвийн ажиллах боломжтойг нотолсон. Харин Chaos туршилтын хүрээнд серверийг 26(45s-1.11m) секундийн турш зориуд унтраахад системд `connection refused` алдаанууд олноор үүсэж, нийт хүсэлтийн амжилттай биелэлтийн хувь 73.25% хүртэл унасан байна. Мөн `/pay` хүсэлтийн алдааны түвшин 29.35% болж өссөн нь серверийн бодит саатал системийн найдвартай байдалд хэрхэн хүчтэй нөлөөлдгийг тодорхой харууллаа. Зөвхөн бэлэн байдлыг цагаар хэмжих нь хангалтгүй бөгөөд сервер унах үед хүсэлт хүлээх цаггүй (latency) шууд буцдаг тул алдаатай хүсэлтийн тоо огцом нэмэгддэг болохыг энэхүү туршилтаас ойлголоо. Тиймээс Availability (бэлэн байдал) болон Reliability (найдвартай байдал) гэсэн хэмжүүрүүдийг хооронд нь тусгаарлаж, health-check endpoint болон бизнесийн логикийн алдаагаар салгаж хэмжих шаардлагатайг анзаарлаа. Үүнээс гадна зориуд SLO босгыг чангаруулсан `fail.txt` туршилтаар k6 нь threshold эвдэгдсэн тохиолдолд `exit=99` гэсэн non-zero exit code буцааж байгааг амжилттай баталгаажуулсан. Энэхүү exit code нь CI/CD pipeline дээр маш чухал үүрэгтэй бөгөөд чанарын шаардлага хангаагүй кодыг цааш production орчин руу нэвтрэхээс автоматаар сэргийлдэг гол механизм юм. Сценарионоос SLO, улмаар k6 threshold руу шилжихэд хамгийн хэцүү нь бодит систем дээрх хэмжүүрүүдийг хэт өөдрөг биш, бас хэт сул биш бодитой тодорхойлох явдал байлаа. Цаашид серверийн бэлэн байдлыг дээшлүүлэхийн тулд саатлын үед автоматаар дахин ачааллах (PM2) болон Load Balancer тохируулах нь зүйтэй гэж дүгнэлээ.
